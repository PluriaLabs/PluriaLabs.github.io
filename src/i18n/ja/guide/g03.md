# Chapter 24: Super Tab で再利用できるテンプレートを作る

フィールドを使うと、固定の展開結果が対話的なフォームになります。フィールドには、プレースホルダ、デフォルト値、選択肢のリストを設定できます。

1. 繰り返し使う構造のマクロを作成します。
2. 展開内容にフィールドを追加するか、ソースを作成しながら **挿入 ▸ フィールド** を使います。
3. マクロを展開します。
4. 選択された最初のフィールドに入力します。
5. **次のフィールド** で先へ進み、**前のフィールド** で戻ります。
6. 選択肢のフィールドでは、フィールドの選択肢リストから選びます。

フィールドは、人が自然に答える順序で設計してください。最後のキャレットは、自由に書き続けたい場所に置きます。デフォルト値は無害なものにしましょう。ユーザーが入力し忘れたフィールドは、誤解を招く内容がそのまま公開されるのではなく、プレビューで一目でわかるようにします。

# Part VII — 数式、ダイアグラム、グラフ、画像

# Chapter 25: 数式、ダイアグラム、グラフを書く

Pilcrow には、MathJax の数式、Mermaid のダイアグラム、Vega-Lite のグラフをオフラインでレンダリングする機能があります。ブロックの開始位置と終了位置は、引き続き有効なプロファイルが決定します。内蔵ライブラリは、その中身を描画するだけです。

## テンプレートから始める

1. **挿入 ▸ 数式**、**ダイアグラム**、または **グラフ** を選びます。
2. テンプレートを選びます。
3. サンプルのソースを置き換えます。
4. プレビューまたは並べて表示に切り替えます。
5. 報告された構文エラーを、ソースブロックで修正します。

数式の表記には MathJax、フローや関係の表現には Mermaid、データに基づくグラフには Vega-Lite を使います。重要なビジュアルの近くには文章での説明を添えておきましょう。そうすれば、レンダラが利用できなくてもドキュメントが理解でき、より多くの読者にとってアクセシブルになります。

これらのライブラリは内蔵されており、ネットワークに接続せずに動作します。設定 ▸ ライブラリ ▸ レンダリングライブラリ には、バージョンと通知が表示されます。ブロックが描画されない場合は、テーマを変更する前に、言語ラベル、区切り文字、オプション機能の設定、構文を確認してください。

# Chapter 26: 画像の挿入とオンライン画像のプライバシーを管理する

**設定 ▸ 編集 ▸ 画像** を開き、次の点を決めます。

- 挿入した画像をコピーするか、移動するか、そのままにするか。
- そのルールをローカルの画像とオンラインの画像の両方に適用するか。
- オンライン画像の読み込みを許可するか。
- 可能な場合にパスを相対パスにするか。
- 相対パスを `./` で始めるか。
- 挿入時に URL をエスケープするか。

持ち運びできるプロジェクトにするには、画像をドキュメントのフォルダ内に置き、相対パスを使います。元の画像が別のプロジェクトのものである場合は、移動よりコピーのほうが安全です。移動すれば重複は避けられますが、元の場所が壊れる可能性があります。

オンライン画像は、閲覧者のネットワークアドレスをホストに知らせてしまううえ、内容が変わったり消えたりすることがあります。信頼できないドキュメントを確認するときは、ネットワークからの読み込みをオフにしておきましょう。長期間にわたって公開するなら、使用許可を得たコピーをダウンロードして、ローカルから参照します。

# Part VIII — 公開と共有

# Chapter 27: HTML、PDF、Word、画像として書き出す

1. ドキュメントを保存し、プレビューで確認します。
2. ツールバーまたはファイルのコマンドから「書き出す」を選びます。
3. HTML、HTML（スタイルなし）、PDF、Word、画像、PDF アーカイブのいずれかを選びます。
4. **スタイル** でレンダリングテーマを選びます。
5. PDF、PDF アーカイブ、Word では、**ページ** のオプション（用紙サイズ、向き、余白）を確認します。
6. **書き出す** を選んで保存先を指定するか、**共有** を選んで生成したファイルをそのまま送ります。

HTML は、スタイル付きの単体ページを作成します。**HTML（スタイルなし）** は、テーマの CSS を埋め込まない、すっきりした構造を出力します。Word は、意味に基づく文書構造を持つ本物の `.docx` パッケージを生成し、補助的な数式、ダイアグラム、グラフは画像になります。**画像** は、レンダリングされたドキュメントを 1 枚の PNG にします。**PDF アーカイブ** は、順序付けられた PDF の分割ファイルとマニフェストを含む ZIP を作成します。別のワークフローで、上限のある分離可能な分割ファイルが必要なときに便利です。通常の大きな PDF は、自動的に分割レンダリングの経路で組み立てられますが、PDF アーカイブでは分割ファイルそのものが成果物として残ります。

**詳細オプション** を開くと、この書き出しだけに適用する **カスタム CSS** を追加できます。書き出しごとの CSS はテーマのあとに適用されるため、セレクタの優先度が同じ場合はこちらが優先されます。ページの変更は現在の書き出しにのみ影響します。ただし **このページ設定を既定として使用** を選んだ場合は別です。生成される目次、見出し番号、見出しラベルは、**設定 ▸ 目次**（Chapter 70）で、すべての書き出しに共通して一度だけ設定します。

出力がおかしいときは、問題が構造にあるのかスタイルにあるのかを見極めます。見出しが欠けているのは、たいていプロファイルやソースの問題です。見出しの見栄えが悪いのは、レンダリングテーマの問題です。

## レンダリングされたドキュメントをプリントする

ファイルまたはその他から **プリント…** を選びます。プリントは、PDF と同じレンダリング処理とページレイアウトの既定値を使います。そのため、構造とスタイルの問題はまずプレビューと PDF の書き出しで調べるのが適切です。Mac では、ページ設定が同じ共有ページレイアウトを編集します。実際に紙に出力する前に、プリントダイアログで用紙、向き、余白、ヘッダ、フッタを確認してください。

# Chapter 28: 書き出しの既定値とページの付属要素を設定する

**設定 ▸ 書き出し ▸ 書き出しの既定値** を開きます。既定のレンダリングテーマとページレイアウトを選びます。作成者のメタデータ、ヘッダ、フッタ、そして最上位の見出しごとに新しいページから始めるかどうか（**最上位見出しの間で改ページ**）を設定します。

ヘッダとフッタのテンプレートには、`${title}`、`${author}`、`${pageNo}`、`${pageCount}`、`${today}` を含められます。ページの余白に収まる短さにしてください。複数ページの PDF で確認しましょう。1 ページでは問題なく見えるヘッダも、あとのページで長い見出しやページ番号とぶつかることがあります。これらの仕上げ用の値は出力形式ごとに保存されます。ページレイアウトは、PDF、PDF アーカイブ、Word、プリントで共通です。

CommonMark のオプションでは、ハイライト、下付き文字、上付き文字、インライン数式、自動リンク、アラート、フロントマター、ダイアグラム、スマート句読点、コードフェンスの表示など、任意の構文を制御します。ソースで実際に使う機能だけを有効にしてください。持ち運びを前提とした CommonMark ドキュメントでは、拡張機能を、その旨を明記せずに前提としてはいけません。

# Chapter 29: ソースと完成した出力を共有する

ほかの人が編集可能なファイルを必要とするときは、ソースドキュメントに対して **共有…** を選びます。保存済みで変更のないドキュメントは、そのまま共有されます。未保存または変更のあるドキュメントは、現在のテキストの一時コピーとして共有されます。非常に大きなドキュメントは、先に保存しておく必要がある場合があります。

受け取る人が完成した PDF、Word 文書、HTML ファイル、画像を必要とするときは、書き出しの **共有** を選びます。これにより、別の書き出しファイルを先に保存しておかなくても、出力が生成されます。

ソースを共有する前に、受け取る人が同じ動作を必要とする場合は、依存しているローカル画像、リンク先のドキュメント、プロファイル、テーマも含めてください。完成した出力を共有する前に、リンク、プレビュー、改ページ、代替テキスト、ファイル名を確認してください。

# Part IX — アシスタント

# Chapter 30: AI プロバイダに安全に接続する

アシスタントは任意の機能で、ユーザーが設定した接続を使います。Pilcrow が黙ってプロバイダを選ぶことはありません。

1. **設定 ▸ 一般 ▸ アシスタント** を開きます。
2. プリセットを追加するか、**カスタム…** を選びます。
3. 名前、ベース URL、ワイヤフォーマット、モデルを入力します。
4. プロバイダが API キーを必要とする場合は、そのオプションを有効にし、求められたらキーを保存します。キーはシステムのキーチェーンに保管されます。
5. **接続をテスト** を選びます。
6. 保存して、その接続を有効にします。

プロバイダがモデルの検出に対応している場合は、アシスタントで **モデルを選択…** を使います。モデルがなくなった場合は、古い識別子を何度も試すのではなく、現行のモデルを選んでください。

接続を初めて使う前に、Pilcrow はテキストの送信先を表示し、同意を求めます。ホスト名をよく読んでください。同じ API 形式でも、ローカルサーバと公開クラウドのプロバイダでは、プライバシーへの影響が異なります。

# Chapter 31: 文脈を意図して選んで質問する

アシスタントのサイドバーを開き、会話モードを選びます。コンテキストチップは、まず最小限で役に立つ範囲、通常は選択範囲から始まります。質問に必要な場合にだけ、別の範囲を選んでください。

1. 助けがほしい段落を選択します。
2. チップに「選択範囲」と表示されていることを確認し、その概要を確認します。
3. 「どの文のせいで時系列がわかりにくくなっていますか?」のように、具体的な質問をします。
4. 返答は、自動的な編集ではなくアドバイスとして読みます。
5. 変更は自分で適用するか、提示された確認済みのアクションで適用します。

Pilcrow は、設定されたパターンとフォルダをアシスタントのコンテキストから除外します。これらはアシスタントの設定で管理します。機密性の高いワークスペースでは、フォルダのコントロールを使ってアシスタントのアクセスをオフにします。会話が現在の作業に関係なくなったら、ゴミ箱ボタンで会話をクリアします。

質問が 1 つのファイルに触れているというだけで、フォルダ全体を共有してはいけません。必要最小限のコンテキストにすることで、プライバシーが向上し、多くの場合、回答の質も上がります。

# Chapter 32: Pilcrow のリソース作成をアシスタントに手伝ってもらう

アシスタントを **ヘルプ** に切り替え、プロファイル、マクロ、スタイルガイドのいずれかを選びます。Pilcrow は関連するフォーマットのリファレンスを会話に含めるため、続けて指示を出しても内容がぶれません。

望む動作を説明し、小さな例を示します。ドラフトを依頼し、プレビューで生成されたリソースのテキストを確認してから、該当する設定エディタで検証します。名前、トリガまたはパターン、出力を読まずに、中身のわからない生成された JSON を読み込んだり保存したりしてはいけません。

効果的な進め方は次のとおりです。

1. 1 つの動作と 2 つの例を示します。
2. 有効な最小限のリソースを依頼します。
3. Pilcrow で検証します。
4. 成功する例を 1 つと、一致しない例を 1 つテストします。
5. 検証エラーを返して、的を絞った修正を依頼します。

# Chapter 33: AI によるスタイルレビューを実行する

このワークフローは Chapter 21 を拡張したものです。

1. 最初の試行のために、一節を選択します。
2. スタイルレビュー、ガイド、バリアント、レビューの対象領域を選びます。
3. 有効なプロバイダとモデルを確認します。
4. レビューを開始します。
5. 提示されたとおりに、重大度または領域で指摘事項を並べ替えます。
6. 指摘事項を開き、引用された根拠を読み、ソース上の位置を確認します。
7. 適用するか、却下するか、未解決のままにします。

ドキュメント全体の場合、Pilcrow はバイト数とリクエスト数を見積もり、送信前にあらためて確認を求めます。チャンクの合間に停止することもできます。機密性の高いドキュメントは、ローカルで、または取り扱い条件に同意できるプロバイダでレビューしてください。接続を廃止するときは、アシスタントまたは「ストレージとプライバシー」の設定から AI のデータとキーを削除します。

# Part X — 書籍プロジェクト

# Chapter 34: フォルダを書籍プロジェクトにする

新しいプロジェクトの場合は、**ファイル ▸ 新しい本…** を選び、タイトルと保存先を入力すると、Pilcrow が最初のフォルダとマニフェストを作成します。既存の原稿を取り込むには、そのフォルダを開き、**ファイル ▸ フォルダを書籍プロジェクトにする** か、プロジェクトサイドバーの **プロジェクトにする** を選び、メタデータを入力します。Pilcrow は、順序とメタデータを記述した `manifest.pilcrow` ファイルを作成します。原稿のファイルを並べ替えることはありません。

プロジェクトの設定を開き、タイトル、作者、目標語数、変数、語数カウントの動作、構文を入力します。**原稿に含まれていません** と表示されている既存のファイルを追加するか、プラスメニューから、前付け、章、シーン、後付けを新規に作成します。

`manifest.pilcrow` は原稿と一緒にコミットまたはバックアップしてください。ソースファイルは通常のテキストのままですが、これがプロジェクトを整理するための目次になります。

# Chapter 35: シーンを計画し、原稿の進捗を追跡する

**リスト**、**あらすじ**、**カード** から選びます。

- リストは、原稿の順序と語数を強調して表示します。
- あらすじは、要約、視点、場所、ステータス、進捗を加えて表示します。
- カードは、ファイルの順序を変えずに使える、視覚的な計画ボードです。

項目の詳細を開いて、役割、ステータス、あらすじ、視点、場所、目標語数を設定します。ステータスで絞り込むと、下書き、改稿、完成のいずれかの作業に集中できます。資料やカットしたシーンなどは、ファイルを削除せずに原稿から項目を外せます。

並べ替えは、ステータスの絞り込みが有効でないときにだけ行ってください。絞り込まれた一部だけでは、原稿全体の順序を正しく表せないためです。iPad では、**並べ替え** を選び、ドラッグしてから **完了** を選びます。章を折りたたむと、リストがすっきりします。

プロジェクトファイルがディスク上で変更されたと Pilcrow が表示したら、再読み込みしてから、やりたかった操作をやり直してください。この競合の保護により、あるデバイスや共同作業者が新しいマニフェストを上書きしてしまうことを防げます。

# Chapter 36: 原稿をコンパイルする

1. プロジェクトサイドバーを開きます。
2. 順序、含めるファイル、プロジェクトのメタデータを確認します。
3. **コンパイル…** を選びます。
4. 出力形式、レンダリングテーマ、コンパイルオプションを選びます。
5. 前付け、章の区切り、番号付け、含める役割を確認します。
6. コンパイルして、結果を確認します。

コンパイルでは、HTML、PDF、Word を作成できます。新しいページから始める前付け、部、章、後付けを選べます。さらに、シーン間の区切りの設定、目次の追加、見出しへの番号付け、含めるすべてのファイルのバージョン履歴のスナップショットを先に残すかどうかも指定できます。原稿の概要には、含まれるファイル、バイト数、除外されたファイル、見つからないパス、最終的な順序が表示されます。見つからないファイルは、解決しないとコンパイルを実行できません。

同じ原稿をいくつもの方法で公開する場合は、コンパイルの選択内容をまとめて名前付きプリセットとして保存します。たとえば「編集者向け DOCX」と「印刷用 PDF」のようにします。不要になったプリセットは、同じシートから削除します。コンパイルの実行中は、進捗にファイル数が表示され、**停止** で処理を中止できます。解決できない `{{variables}}` は報告され、そのまま見える形で残されます。

コンパイルは、マニフェストの順序を読み取り、ソースを論理的に結合します。ファイルを連結して上書きすることはありません。シーンを直すときは、そのソースファイルを修正してから、もう一度コンパイルしてください。繰り返し使うメタデータには、タイトルや作者のテキストを手作業で複製するのではなく、プロジェクト変数を使いましょう。

# Part XI — 構文プロファイル

# Chapter 37: 構文プロファイルを選び、理解する

プロファイルは、ソース上の記号がどのように構造上の役割になるかを Pilcrow に伝えます。CommonMark は内蔵されていますが、あくまで 1 つのプロファイルであり、アプリの定義そのものではありません。

プロファイルを選ぶには、ステータスバーのプロファイルのコントロールか、それに該当するドキュメントのコントロールを使います。Pilcrow は拡張子からプロファイルを推測でき、ファイルごとの選択を記憶します。有効なプロファイルは、ハイライト、アウトライン、書式の利用可否、プレビュー、書き出しの構造、継続動作、プロファイル固有の挿入を決定します。

すでにあるソースの言語に基づいてプロファイルを選んでください。プロファイルを変えてもテキストは変換されません。解釈し直されるだけです。変換が必要な場合は、コピーを作って、ソースを明示的に変換します。

# Chapter 38: プロファイルを作成してテストする

1. **設定 ▸ ライブラリ ▸ 構文プロファイル** を開きます。
2. 近い内蔵プロファイルを複製するか、新しいプロファイルを作成します。
3. **概要** で、名前、識別子、拡張子、必要に応じて継承を設定します。
4. **ルール** で、必要な最小限の構成要素を追加します。
5. **テストサンプル** を開き、代表的なソースを貼り付けて、**サンプルをチェック** を選びます。
6. 保存し、使い捨てのドキュメントでプロファイルを有効にして、編集、アウトライン、プレビュー、書き出しを比較します。

境界をテストします。ファイルの先頭と末尾、空行、入れ子の構成要素、Unicode、閉じていない区切り文字、一致してはいけないテキストです。プロファイルが信頼できるのは、例を認識するだけでなく、惜しい例をきちんと拒否できるときです。

動作確認済みのリビジョンができたら、**新しいベースラインとして設定** を使います。**ベースラインに戻す** を選ぶと、その後の試行はすべて破棄されます。大胆な再設計の前には、複製しておきましょう。

# Chapter 39: プロファイルのルールと詳細な JSON を編集する

ルールエディタでは、パターンの種類、行頭の要件、生成される役割、キャプチャ、Return 後の継続、区切りブロックの動作、レイアウト、インラインのランとペア、キャプション、スタイルの役割を設定できます。

構文を表現できるなら、リテラルまたは構造化された認識方法を使ってください。パターンは範囲を限定し、アンカーで固定します。Pilcrow は既知の安全でないパターンを拒否しますが、技術的に受け入れられた式でも、広すぎたりわかりにくかったりすることはあります。

**詳細な JSON を編集…** を選ぶのは、ビジュアルエディタでは必要なプロパティを扱えない場合だけにしてください。適用すると JSON が検証され、このシートからプロファイルの識別情報を変更することはできません。詳細な作業をするときは、有効なテストサンプルも手元に置いておきましょう。

継承は、小さな方言を作るのに便利です。安定した親を継承し、名前を指定した構文だけを置き換えます。動作の説明が難しくなるような長い継承の連鎖は避けてください。プロファイルの読み込みで競合が報告された場合は、何かを置き換える前に、名前と ID を比較してください。
